# 과제 제출 점검

과제 안내문(제출 형식, 허용 링크, 체크리스트)이 대화에 있으면 그것이 우선이다.
없으면 사용자에게 "제출란이 받는 링크 종류"만 한 줄로 묻는다.

## 1. 상태 확인 (읽기만 한다)

적용 대상 프로젝트의 루트에서 실행한다.

1. `git status -sb`: 커밋하지 않은 변경, 푸시하지 않은 커밋이 있는지 본다.
2. `git remote -v`: 원격이 없으면 "GitHub에서 빈 저장소를 만들어 주소를 알려 달라"고 하고 멈춘다.
3. `git ls-files`: 제출물(코드, README, 스크린샷 등)이 실제로 추적되는지 본다. `.gitignore` 때문에 빠진 것이 없는지도 본다.
4. `.env`, 키, 토큰, 개인정보가 추적되거나 README에 들어가 있지 않은지 검색한다. 있으면 제출 전에 먼저 알린다.

## 2. README 점검

최상단 `README.md`에 아래가 있는지 본다. 없는 항목은 저장소 안의 내용만 근거로 초안을 쓴다. 지어내지 않는다.

- **왜**: 어떤 불편이 있었고 이 결과물이 어떻게 해결했는지
- **실행·접속 방법**: 설치 위치나 접속 주소
- **확인한 결과**: 실제로 해 본 것만. 해 보지 않은 것은 "미확인"이라고 적는다
- 게임·웹 서비스라면 **상대경로(`../x/index.html`) 대신 실제 접속 주소** 링크. 상대경로는 GitHub 화면에서 코드만 보여 준다

## 3. 배포 링크 확인 (웹 결과물일 때)

- GitHub Pages 주소(`https://<아이디>.github.io/<저장소>/…`)를 `curl -sI` 등으로 열어 응답 코드를 확인한다.
- 이 확인은 "열린다"까지만 말해 준다. 조작이 되는지는 사용자가 직접 확인해야 한다고 알린다.

## 4. 고치기 전에 허락받기

README 수정, 커밋, 푸시는 저장소 내용을 바꾸므로 **무엇을 어떻게 바꿀지 보여 주고 사용자가 "응"이라고 한 뒤에** 한다.
허락을 받으면 변경 파일만 `git add`(`-A` 금지), 커밋, `git push`를 하고 푸시 후 원격에서 다시 받아 반영을 확인한다.

## 5. 마지막 보고 (짧게)

- 제출란에 낼 링크 1개를 코드 블록으로 준다.
  - 제출란이 `github.com`/`drive.google.com`만 받으면 `github.io` 주소를 제출 링크로 주지 않는다. 그 주소는 README 안에 넣는다.
  - 저장소 안 파일을 가리킬 때는 `https://github.com/<아이디>/<저장소>/blob/main/<경로>`
- 사용자가 직접 해야 할 일을 목록으로 준다: 로그인과 제출 버튼, 시크릿 창/휴대폰 확인, 회고·마무리 문장.
  회고와 마무리 문장은 사용자의 경험이라 **대신 쓰지 않는다**.
- 끝낸 것과 확인하지 못한 것을 구분해서 말한다.
